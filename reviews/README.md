## Layout and lifecycle

```
reviews/
  README.md                          <- this file: rules + registry
  YYYY-MM-DD_<external|internal>_<scope>/   <- NEW, not yet processed reviews land here (top level)
      REVIEW.md (or the reviewer's own file names, kept as delivered)
      <reviewer's scripts and data>
  archive/
    YYYY-MM-DD_<external|internal>_<scope>/ <- processed reviews (moved here when done)
      ...review files...
      RESPONSE.md                    <- written by us
```

- **external**: an independent third party (a person, or a model/session outside the working session). Its text is
  kept verbatim.
- **internal**: a check run within the project by a working session or subagent. The same separation between
  reviewer and responder applies as for external reviews.
- The date is the date the review was delivered. The scope is a short slug.

**Lifecycle.**
1. **New reviews are written to the top level of `reviews/`,** one folder per review.
2. **Check for new reviews periodically**, at the start of every work iteration and before any final report. Any
   folder at the top level of `reviews/` other than `archive/` is unprocessed.
3. **The review's author must not process their own review.** Owner's instruction, 2026-10-15:
   "тот кто пишет ревью - не обрабатывает его". The reviewer leaves the delivered review awaiting a different
   participant; changing roles within the same review does not make self-processing valid.
4. **Processing** is a separate pass by someone other than the review's author: check the findings and record
   decisions in `RESPONSE.md`. Each finding is fixed and verified, rejected with a reason, or explicitly deferred
   with a reason and tracked in `../STATUS.md`. Update the affected documentation (READMEs, `lfphys/LAYERS.md`, module
   passports).
   Creating a response file or copying the review's recommendations into STATUS alone does not constitute processing.
5. **Only the responder archives a processed review.** After the pass above is complete, move the folder to
   `reviews/archive/` and update the registry below. Fix links to it elsewhere, and only the root path in reviewer
   scripts (marked by a comment). A request to write a review does not include processing or archiving that review.

## Rules for reviewers

1. Write only inside your own review folder. Do not modify research files.
2. Make checks reproducible (scripts plus their outputs, stated environment), and cite sources so they can be
   verified.
3. Mark each finding with a severity (error / should-fix / nit) and give a location and, if possible, a fix.
4. Deliver the review in `reviews/`, with status **awaiting processing**. Do not write your own `RESPONSE.md`,
   decide acceptance/rejection on behalf of the project, or move your review to `archive/`.

## Rules for responding (us)

1. **Do not process a review you authored.** Leave it for a different participant.
   **Never edit a review text.** The only exceptions are moving it and fixing paths that a move broke in reviewer
   scripts; mark such a fix with a comment.
2. **Respond in `RESPONSE.md`.** For each finding give:
   - its ID;
   - a one-line summary;
   - the decision: *fixed* / *partly fixed* / *rejected (with reason)* / *open → STATUS.md*;
   - where the fix is (files);
   - how it was verified (tests or checks).
3. **Every accepted finding is either fixed or entered as a gap in `../STATUS.md`.** Nothing is silently dropped.
4. **Corrections are visible.** Corrected results are tagged `[error in earlier]` in `RESPONSE.md` and in the
   affected documentation, so that no README, passport or check note keeps a withdrawn statement.
5. **Quotes and numbers taken from a review are verified against the original source** before they are used.
