# lfphys: a physics engine with interactive visualizations

A Python library with the physics that the visualizations in `../visualizations/` wrap. A visualization takes its
physics from here and keeps only orchestration (time line, events, apparatus logic) and drawing.

What goes where is set by the owner's instruction (2026-10-23, quoted in `LAYERS.md`):

* **core**: established physics only. Each law is computed exactly or with an error that is stated and tested for the cases in its tests. Each function
  is tested against a closed form or a second, independent method.
* **outside the core**: theories physicists use widely that disagree with the core or with each other somewhere. These
  are approximations, interpretations, phenomenological models, and alternatives for "what if" worlds.

The rules are in `LAYERS.md`; `tests/test_layers.py` checks them.

## Using it

* **Runtime.** Run it in the visualization image, `lfphys-viz` (see `../visualizations/docker/`). It needs
  numpy and scipy; the certified references also need python-flint 0.9.0, pinned in the image.
* **Import path.** The visualization server puts the engine on the import path. For a separate script:
  `PYTHONPATH=<this repository>/lfphys`.
* **Catalogue.** Every module carries `ABOUT = {layer, kind, title, statement, validity, basis, conflicts}`.
  * `lfphys.registry.catalogue()` lists all modules.
  * `registry.describe(names)` returns the entries one world uses. The player shows them in the panel "Physics of this
    world".
  * A module may split its entry into parts (`DATASETS`). A world that reads only some data names the part:
    `"core.data:air"` is the air's own entry, not the whole data module's.
  * **Languages.** The user-facing fields of `ABOUT` and every other text the engine gives a user (refusals, notes,
    labels) are translatable texts `lfphys.i18n.T("English msgid {arg}", arg=value)`, rendered in the viewer's
    language from `lfphys/locales/<lang>.json` (`LAYERS.md` §2 rule 1, `../visualizations/RULES.md` §7).

```
docker run --rm --user "$(id -u):$(id -g)" -v <this repository>:/lf -w /lf/lfphys lfphys-viz \
    python3 -m pytest -q -p no:cacheprovider
```

## CPU and GPU (plan P11)

Heavy kernels register with `core.backend` and ask it where to run: on the CPU (NumPy) or on GPU 0 (CuPy with the
NVIDIA CUDA 12 runtime from PyPI, pinned in the Docker image). "Auto" (the default) takes the GPU only where it is
faster — measured: the angular spectrum from 128×128 points (×2) to ×9 at 2048×2048 including the transfers; the
light-time ray tracer from 256×256 pixels with 12 bodies (×3.8) to ×7 at 512×512; the Kerr shadow tracer from
256×256 pixels (×3.2) to ×13 at 512×512; the 2-D/3-D split operator from
128×128 points (×3) to ×26–29 at 1024²–2048² (four steps on the device, the density back); the FDTD stepper (B8) from 128² cells (×2.3) to ×67 at 4096² in 2-D and from ×6 at 32³ to ×76 at 256³ in 3-D, bit-identical to the CPU for real fields (its device choice counts the plane waves' tables, the DFT accumulators and the dispersive nodes, review B8-fdtd F18). Kernels
without a GPU gain stay on the CPU and say why (Arb references, sequential ODEs, small transfer matrices, the 1-D
Schrödinger stepper). fp64 by default; fp32 only for kernels whose fp32 error is validated by a test, and only for
results that are drawn; references and checks are always fp64; fp16 is not offered. Without a GPU everything runs on
the CPU with the same code. Tests with the GPU: add `--gpus '"device=0"'` to the `docker run` command.

The image carries the CUDA 12.9 runtime (PyPI wheels) while this host's driver 550 reports CUDA 12.4. This works
through CUDA minor-version compatibility: NVIDIA's guide (docs.nvidia.com/deploy/cuda-compatibility, "Minor Version
Compatibility", fetched 2026-10-27) gives "CUDA 12.x", ">= 525" as the minimum driver and warns that "Applications that
compile device code to PTX will not work on older drivers"; CuPy avoids PTX by default ("By default, CuPy directly
compiles kernels into SASS (CUBIN) to support CUDA Enhanced Compatibility", CuPy docs, `CUPY_COMPILE_WITH_PTX`,
default 0). So `CUPY_COMPILE_WITH_PTX` must stay unset; a driver of CUDA 12.9 or newer removes the dependence.

Memory: "auto" takes the GPU only when the kernel's footprint fits in 80 % of its free memory; a call that still
runs out of GPU memory is redone on the CPU (the reason recorded); after each GPU call the memory pool is returned,
so an idle run holds only its CUDA context (~160 MB). GPU 0 is pinned by its PCI bus id (`LFPHYS_GPU_PCI`,
`CUDA_DEVICE_ORDER=PCI_BUS_ID`; the compose service sets both).

## Certified references (Arb)

`core.certified` evaluates key quantities in ball arithmetic. Each result is an interval that, if the implementation is correct, contains
the exact value, reached by an independent route rather than by re-running the float code. The engine tests compare
the float64 results against these intervals.

This has already found one real defect. The large-argument Hankel asymptotics lost precision at x = 1e8, through the
phase factor; it is fixed in `core.optics.scalar`.
